# Fiorify — Stage S2: Tenant Data Isolation & Boundary Verification

## 1. Tenant Boundary Model
Fiorify enforces strict multi-tenant boundary controls across all storage, caching, and runtime layers.
Every customer dataset must carry tenant provenance (`tenant_id`).

### Protected Resources:
1. **Modernization Assessments**: Scoped to the customer tenant.
2. **Generation Studio Projects**: Independent development workspaces isolated per tenant.
3. **Generated Artifacts**: Custom ABAP code, Core Data Services (CDS), and UI5 manifests restricted to the owning tenant.
4. **SAP Landscape Systems**: Connection definitions, client numbers, and system profiles partitioned by tenant.
5. **Security Audit Trails**: Cryptographic integrity chains calculated and verified on a per-tenant partition.

---

## 2. Enforcement Mechanisms

### 2.1 API Route Handlers (`server.js`)
When an authenticated request accesses an entity by ID:
1. The domain entity is fetched.
2. The entity's `tenantId` is compared against `currentUser.tenantId`.
3. If unequal, execution halts immediately:
   - Status: HTTP 403 Forbidden
   - Error code: `TenantAccessDenied`
   - Security audit event: `TENANT_ACCESS_VIOLATION` logged to PostgreSQL.

### 2.2 Database Pool Session Reset (`pool.js`)
When pooling PostgreSQL connections across requests from different tenants:
```javascript
await DatabasePool.withTenantClient(tenantId, async (client) => {
  await client.query("SET LOCAL app.current_tenant = $1;", [tenantId]);
  // Execute tenant work...
});
```
Upon completion (whether success or error), `finally { await client.query('DISCARD ALL;'); client.release(); }` is executed, clearing all session variables, prepared statements, and temporary tables. No context leaks across client reuses.
